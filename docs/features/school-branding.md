# School branding

Each installation manages one school. System Settings → School Branding uses the existing `school_settings` singleton and `App\Support\Settings\SystemSettings`; reports and future documents can resolve the same identity and assets through that service.

## Configuration

Users with `settings.update` can save identity text, four branding images, six primary-color presets, and developer attribution. Users with `settings.view` have read-only access. Public login pages render only public branding. Personal appearance remains in `users.theme`.

Text and color edits are previews until Save Changes. Confirmed restore controls immediately reset only the selected saved value. The default accent is blue. Status palettes remain independent of the school accent. The copyright year uses the configured school timezone.

PNG, JPEG, and WebP logos accept up to 2 MB: sidebar logos up to 2048 × 2048 and login images up to 2560 × 2560. Favicons accept PNG, WebP, or ICO up to 512 KB; raster favicons are limited to 512 × 512. Upload names are generated by Laravel. Dark and login images fall back to the primary logo, then the bundled default. Favicon fallback is the bundled `public/favicon.ico`.

## Deployment

1. Back up the school database and `storage/app/public` together.
2. Run `php artisan migrate --force --no-interaction` during the normal deployment to apply the existing additive branding migration. It adds nullable preferences without rewriting school settings. Never use database-reset commands to deploy this feature.
3. Persist `storage/app/public/branding` across releases. The PHP application must be able to write there, and to its usual cache and temporary-upload directories. Do not replace persistent storage with an empty release directory.
4. Run `php artisan storage:link --no-interaction` when setting up a server. The web server must serve `public/storage` from `storage/app/public`; it must not execute uploaded files as scripts.
5. Set `APP_URL` to the installation's public HTTPS URL before rebuilding Laravel's configuration cache. The public disk derives its asset URL from `APP_URL`. Configure proxy HTTPS handling as appropriate for the hosting environment.
6. Build frontend assets for this code release using `npm ci` and `npm run build`. Subsequent branding changes do not require a frontend rebuild. Regenerate the normal application caches during deployment so old compiled views are not retained.

Use the existing production cache store consistently across application instances. Saving settings invalidates the shared settings cache and in-process resolution. Custom-asset existence checks are cached for five minutes to avoid repeated filesystem access. If an asset is removed outside System Settings, its server-side fallback can take up to five minutes to refresh. Use System Settings to replace or remove images.

Replacement stores the new upload before changing the database. Old custom images are removed after commit only when no branding field references them. A failed save or surrounding transaction rollback cleans up new uploads and retains the previous image. Filesystem cleanup failures are reported to the application log; investigate storage permissions if obsolete files accumulate. Bundled defaults are never deleted.

## Verification

Run the branding and settings tests using the repository's dedicated MySQL testing database:

```shell
php artisan test --compact tests/Feature/SchoolBrandingTest.php tests/Feature/SystemSettingsTest.php tests/Feature/SystemSettingsAuthorizationTest.php
```

Before deployment, also run the application suite, Pint, PHPStan, and the frontend production build. Browser checks should include both appearance modes, narrow screens, color selection and reset, selected image previews, and public login branding.
